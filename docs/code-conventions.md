# 코드 규약 — 주석·KDoc

이 저장소의 Kotlin 코드에 적용되는 주석·KDoc 규약이다. 문서 트리의 범위 지도는
[`docs/index.md`](index.md)가 적고, 작업 유형 라우팅은 저장소 루트
[`AGENTS.md`](../AGENTS.md)가 정본이라 여기 중복하지 않는다.

## 기준 셋

1. **코드가 이미 말하는 것은 쓰지 않는다.**
2. **뻔하지 않은 의도와 함정은 쓴다.** 왜 이 선택을 했는지, 무엇을 밟으면 깨지는지.
3. **다른 곳의 현재 상태는 쓰지 않는다** — 낡기 때문이다. 아래 [수명](#수명이-기준이다) 참고.

주석의 분량은 그 코드의 **어려움**에 비례해야지 그 코드의 **중요함**에 비례하면 안 된다.

## KDoc에 고정 틀을 쓰지 않는다

"의도 / 반환값 / 파라미터"를 **항상 있는 섹션으로 두지 않는다.** 빈 슬롯을 채우려는 압력이
그 자체로 노이즈를 만든다.

- **의도 한 줄**은 거의 항상 있다.
- **`@return`은 타입과 이름이 말하지 못할 때만.** `fun toTagColor(): TagColor`에
  "@return 태그 색"은 순수 노이즈다.
- **`@param`은 이름이 오해를 부를 때만.** 예: 알림의 `key`가 시스템 `StatusBarNotification.key`인지
  Pushlog DB의 행 id인지 헷갈릴 자리라면 적는다.

## 수명이 기준이다

**코드보다 빨리 낡는 주석은 아예 없는 편이 낫다.** 틀린 주석은 없는 주석보다 나쁘다 —
읽는 사람이 그것을 믿고 움직인다.

가장 잘 낡는 것은 **다른 컴포넌트의 현재 상태**를 기술한 문장이다. 다른 앱이 알림에 무엇을
싣는지, 다른 파일에 무엇이 있는지, 어느 화면이 아직 이 값을 안 읽는지. 특히 메신저·카드사
알림 형식은 앱 업데이트 한 번에 바뀐다. "카카오톡은 `conversationTitle`을 안 준다" 같은
단정은 근거 문서를 가리키는 포인터로 쓴다.

**의도는 남고 상태는 변한다.** 써야만 한다면 낡아도 해가 없게 쓴다 — 단정 대신 근거 문서를 가리킨다.

### 기준 2와 3이 겹칠 때는 남긴다

"다른 컴포넌트가 이 값을 **안 쓴다**"류는 상태 서술이면서 동시에 **오해를 미리 막는 함정 정보**다.
둘 중 어느 쪽인지 애매하면 **지우지 말고 포인터로 바꾼다.** 틀린 주석은 읽는 사람이 알아채지만,
없는 주석은 그가 이미 잘못된 길로 간 뒤에야 드러난다.

**최소 보존선**: 지울 때 그 정보가 어느 문서에 살아 있는지 확인하고, 없으면 **문서로 먼저 옮긴 뒤**
코드에 포인터를 남긴다. 코드에서 지웠는데 문서에도 없으면 그건 정리가 아니라 유실이다.

## 아키텍처 결정은 코드가 아니라 문서에 쓴다

"이 셋 중 왜 하나만 이렇게 했나", "왜 공용화하지 않았나" 같은 결정은
[`architecture/`](architecture)·[`adr/`](adr) 몫이다. 코드에는 **포인터 한 줄**만 둔다.
같은 결정 설명을 여러 파일에 복사하면 결정이 바뀔 때 전부 낡는다.

## 알림 원문을 주석·로그에 넣지 않는다

테스트 픽스처 외의 코드 주석, 로그, 예외 메시지에 실제 알림 원문·발신자·대화방 이름을 넣지 않는다.
"알림 내용은 폰 밖으로 나가지 않는다"는 약속과 Crashlytics 전송 규칙(설계 스펙 §3)에 걸린다.
예시가 필요하면 지어낸 값을 쓴다.

## 서브에이전트에게 실어 나른다

구현·리뷰를 서브에이전트에 디스패치할 때 이 문서를 브리프에 링크한다.
`writing-plans`로 계획을 쓸 때는 계획의 **Global Constraints**에도 넣는다.
최소한 이 넷은 요지로 실어 나른다:

- 코드가 이미 말하는 것은 쓰지 않는다
- `@return`·`@param`은 타입·이름이 말하지 못할 때만
- 다른 컴포넌트의 현재 상태를 단정하지 않는다(낡는다)
- 알림 원문을 주석·로그·예외 메시지에 넣지 않는다
