# Pushlog 설계

- 작성일: 2026-11-13
- 상태: 초안 (사용자 승인 전)
- 범위: 앱 전체 기능 지도와 데이터 구조. MVP 범위는 이 문서 승인 후 별도로 자르고, 구현 계획은 MVP 단위로 쓴다.

## 1. 의도

Pushlog는 서버 없이 기기 안에서 푸시 알림을 수집·저장·분류·정리하는 Android 앱이다.

사용자가 원하는 것은 두 가지다.

1. **설치 이후 모든 알림이 남는다.** 지난 알림을 검색하고, 본문을 복사하고, 원래 앱으로 이동할 수 있다.
2. **분류 기준을 사용자가 정한다.** 앱이 기본 분류(예: 결제)를 주지만, 사용자가 앱(예: 네이버페이)이나 키워드를 넣어 자기 기준으로 바꿀 수 있다.

### 시장 근거 (2026-11-13 Play 스토어 최신 리뷰 기준)

| 앱 | 규모 | 반복되는 불만 |
|---|---|---|
| 노티세이브 | 1,000만+ | 진입 광고 강제, 주간 구독(약 2만 원), 강제 다크모드, 첫 로딩 지연, 저장 알림 눌러도 앱 안 열림, 단톡방 대화가 개인별로 쪼개짐, 리스너가 꺼지고 설정이 풀림 |
| 노티스토리 | 100만+ | 수집이 되다 안 되다 함, 일부 앱 누락, 단톡방 쪼개짐, 오래된 기록 자동 삭제, 그룹 편집·일괄 선택·내보내기 없음. 개발자 답변 0건 |
| NotiFold | 100+ (신규) | 자동 분류를 사용자가 못 고침, 일괄 삭제 없음, 다크모드 가독성 |

세 앱에 공통인 빈자리는 **수집 안정성**, **대화방 단위 묶기**, **사용자 통제권**이다. Pushlog의 차별점은 이 중 사용자 통제권(커스텀 분류)과 영구 기록이고, 나머지 둘은 기본으로 갖춰야 할 품질이다.

## 2. 목표 · 비목표 · 반목표

### 목표

- 알림 접근 권한을 켠 이후의 알림을 빠짐없이, 영구히 기록한다.
- 기록은 검색·복사·원래 앱 이동이 된다.
- 메신저 대화는 대화방 단위로 묶인다. 단톡방이 발신자별로 쪼개지지 않는다.
- 분류는 태그 방식이고, 사용자가 규칙을 만들고 고칠 수 있으며 과거 기록에도 소급된다.
- 알림창 정리는 사용자가 고르는 선택 모드다.
- 결제·배송·쿠폰 정보를 알림에서 추출하고, 지원 기기에서는 AI 질의를 제공한다.

### 비목표

- 수익 모델(BM). 광고·광고 제거 구매는 이번 설계에서 완전히 뺀다. 광고 슬롯이나 정책 인터페이스 같은 사전 준비도 하지 않는다.
- 서버, 계정, 기기 간 동기화.
- 택배사 실시간 조회처럼 외부 API를 호출하는 기능.
- 설치 이전 알림의 복구 (OS가 제공하지 않는다).

### 반목표 (기술적으로 돌아가도 실패로 보는 것)

- 알림 원문·발신자·대화방 이름이 기기 밖으로 나간다.
- 사용자가 설정하지 않았는데 알림창의 알림이 사라진다.
- 규칙을 바꿨는데 과거 기록에는 반영되지 않는다.
- 사용자가 모르는 사이 수집이 멈춘 채로 방치된다.

## 3. 제약

### 플랫폼

- 수집은 `NotificationListenerService` 하나로 한다. 사용자가 시스템 설정에서 알림 접근을 직접 허용해야 한다.
- Android 15+는 OTP 같은 민감 알림의 본문을 일반 리스너에게 가린다. 인증번호 추출은 일부 기기에서 동작하지 않는다.
- 삼성·샤오미 등 OEM 배터리 최적화가 리스너를 죽인다. `requestRebind`와 배터리 최적화 예외 안내가 필요하다.
- 알림의 `contentIntent`(`PendingIntent`)는 알림이 지워지거나 재부팅되면 무효가 되고 영속 저장할 수 없다.

### 네트워크와 프라이버시

- `INTERNET` 권한을 가진다. 용도는 Firebase Crashlytics, Firebase Analytics, (선택 시) Remote Config 수신뿐이다.
- 사용자 약속은 **"알림 내용은 폰 밖으로 나가지 않는다"**이다.
- Crashlytics는 기본 활성, Analytics는 설정에서 동의한 경우에만 수집하고 언제든 끌 수 있다.
- **금지 규칙**: 알림 원문, 발신자, 대화방 이름을 예외 메시지, 로그, Crashlytics 키, Analytics 이벤트 파라미터에 넣지 않는다. 패키지명·개수·소요 시간 같은 메타데이터만 보낸다. 파싱 실패 예외에 원문이 실리기 쉬우므로 리뷰 체크 항목으로 둔다.
- Play 데이터 안전 섹션과 개인정보처리방침에 위 범위를 신고한다.

### 프로젝트 기반

- `android-project-starter-with-llm`으로 생성한 멀티모듈 구조(`app`, `core:*`, `data`, `domain`, `feature:*`, `konsist`) 위에서 만든다. 스택은 Kotlin, Jetpack Compose, Material 3, Hilt, Room, DataStore, Navigation 3, WorkManager.
- 스타터가 넣은 Retrofit과 `feature:sample`은 이 앱에 필요 없으므로 걷어낸다.
- minSdk 26. API 30 미만에서는 대화방 바로가기 정보가 없으므로 대체 로직을 쓴다(§6.2).

## 4. 접근 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 원본 기록 + 다시 계산 가능한 파생 데이터 (채택)** | 리스너는 extras를 원본 그대로 append-only로 저장한다. 대화방·태그·추출 결과는 원본에서 계산한 파생 테이블이고, 규칙이 바뀌면 다시 계산한다. | 태그 규칙·추출 규칙 변경이 과거 기록에 소급된다. 파서 버그를 고치면 기록도 복구된다. 메신저 형식이 바뀌어도 원본이 남는다. | 저장 공간 약 2배. 재계산 작업 관리가 필요하다. |
| B. 수신 시점에 정리해서 저장 | 리스너가 받는 즉시 파싱해 정리된 형태만 저장한다. | 단순하고 작다. | 버린 필드는 되살릴 수 없다. 과거 기록에 새 규칙을 적용할 수 없다. |

B는 "규칙을 바꾸면 과거에도 적용"이라는 핵심 약속과 충돌해서 제외했다. 사용자가 A를 골랐다.

## 5. 데이터 흐름

```
NotificationListenerService
   │ onNotificationPosted / onNotificationRemoved / onListenerConnected(getActiveNotifications)
   ▼
[원본 계층]  raw_notification  (append-only, 수정 금지. 예외는 §6.9의 영구 삭제뿐)
   │ 저장 직후 + 규칙 변경 시 재계산 (WorkManager)
   ▼
[파생 계층]  conversation / message / notification_entry / tag_assignment / extracted_*
   ▼
UI (검색 · 대화방 · 태그 · 결제/배송/쿠폰 · AI 질의) / 알림창 정리 동작
```

- 원본 계층이 단일 출처다. 파생 계층은 언제든 지우고 원본에서 다시 만들 수 있어야 한다.
- 원본에서 다시 만들 수 없는 **사용자 데이터**는 파생 계층과 분리해 저장하고, 재계산이 건드리지 않는다. 해당하는 것: 수동 태그 지정(§6.4), 등록한 쿠폰(§6.7), 삭제 표시(§6.9), 사용자 규칙과 설정.
- 재계산은 범위를 좁힐 수 있어야 한다(전체, 특정 패키지, 특정 기간). 규칙 하나를 바꿨다고 수만 건 전체를 매번 다시 돌리지 않는다.
- 수신 직후의 파생 처리는 화면에 즉시 보여야 하므로 리스너 경로에서 바로 하거나 짧은 지연 안에 끝나야 한다. 구체적 방식은 빌더가 정한다(§9).

## 6. 기능

### 6.1 기록

- 권한이 켜진 이후의 모든 알림을 저장한다. 기본 보관 기간은 무제한이고, 사용자가 설정에서 기간을 정할 수 있다.
- 권한을 켠 순간과 리스너 재연결 때 `getActiveNotifications()`로 알림창에 떠 있는 알림을 가져온다.
- 같은 알림의 갱신(같은 key로 다시 post)은 별개의 원본 행으로 남기되, 파생 계층에서 중복을 제거한다.
- 저장 대상은 extras 전체(직렬화 가능한 값), 패키지, key, tag, id, channel, category, `shortcutId`, `isGroupConversation`, post 시각, 제거 시각과 제거 사유다.
- 이미지는 저장하지 않는다(`largeIcon`의 앱 아이콘 정도는 빌더 판단, §9).
- 메신저는 같은 key로 다시 post할 때마다 최근 메시지 전체를 다시 담는다. 그래서 원본 용량이 "약 2배"보다 훨씬 커질 수 있다. 원본은 내용을 바꾸지 않되 압축해서 저장하고, 설정에 저장 공간 사용량을 보여 준다. 실제 증가량은 첫 단계(§11)에서 측정해 필요하면 이 결정을 다시 연다.

### 6.2 대화방 묶기 (메신저)

2026-11-13 실기기(카카오톡 26.x, One UI) `dumpsys notification --noredact`로 확인한 사실:

- 카카오톡은 대화방마다 알림 하나를 만들고, `shortcut=<방 ID>`가 방마다 고유하다.
- `android.isGroupConversation`이 단톡방은 `true`, 1:1방은 `false`.
- `android.title`은 방 이름이 아니라 **마지막 발신자**다. `android.conversationTitle`은 없다. 기존 앱들이 단톡방을 쪼개는 원인이다.
- 화면의 방 이름은 `ShortcutInfo.shortLabel`에서 온다. 리스너는 `Ranking.getConversationShortcutInfo()`(API 30+)로 읽는다. dump에서 라벨 값은 가려져 있어 실제 값은 구현 첫 단계에서 확인해야 한다.
- `android.messages`에 최근 메시지가 누적돼 들어오고, 각 메시지에 `sender`, `text`, `time`, `extras.chatLogId`가 있다.

규칙:

- 대화방 키는 `패키지 + shortcutId`. 방 이름은 표시용이며 바뀌면 갱신한다.
- 메시지 중복 제거 키는 `chatLogId`가 있으면 그것, 없으면 `sender + time + text`.
- `shortcutId`가 없으면(API 30 미만, 바로가기를 안 쓰는 앱) `conversationTitle` → `title` 순서로 대체한다. 이 경우 쪼개짐이 남을 수 있음을 받아들인다.
- 수집할 수 없는 경우: 알림을 꺼 둔 방, 메신저 앱의 "알림 내용 숨김", 사진·이모티콘(텍스트 대체 문구만 온다).

### 6.3 검색 · 복사 · 원래 앱 이동

- 검색은 본문, 제목, 발신자, 방 이름 대상이고 앱·태그·방·발신자·기간으로 거를 수 있다.
- 한국어는 띄어쓰기 없이 붙는 경우가 많다. "결제완료"를 "결제"로, "완료"로 찾을 수 있어야 한다. Room FTS4 기본 토크나이저는 단어 중간 일치가 안 되므로 방식은 빌더가 정한다(§9).
- 복사: 길게 눌러 개별 복사, 다중 선택 복사.
- 원래 앱 이동: `contentIntent`가 살아 있으면(메모리 캐시) 그것을 실행해 해당 화면으로 간다. 무효면 앱 런처 인텐트로 앱 첫 화면만 연다. 화면에서 두 경우를 구분해 보여 준다.

### 6.4 태그 분류

- 알림 하나는 조건에 맞는 모든 태그를 가진다(폴더가 아니라 태그).
- 앱이 기본 태그와 기본 규칙을 제공한다(예: 결제, 배송, 쿠폰, 메신저, 광고). 사용자는 기본 규칙을 고치거나 끌 수 있고 새 태그와 규칙을 만들 수 있다.
- 규칙 조건은 **앱 지정**과 **키워드 포함/제외**의 조합이다. 예: "결제" 태그에 네이버페이 앱 추가. 토스처럼 한 앱에서 결제와 광고가 섞이는 경우 키워드로 가른다.
- 규칙을 만들거나 고치면 과거 기록에 소급한다(§5 재계산).
- 어떤 태그에도 걸리지 않은 알림은 "태그 없음"으로 모아 보여 준다.
- 사용자가 개별 알림의 태그를 직접 붙이거나 뗄 수 있다. 수동 지정은 규칙 재계산이 덮어쓰지 않는다.
- 정보 추출(§6.7)에 성공한 알림에는 해당 기본 태그가 자동으로 붙는다.

### 6.5 알림창 정리 (선택 모드)

- 설정에서 **기록만**(기본값)과 **알림창 정리까지** 중 고른다.
- 정리 모드에서는 태그마다 동작을 고른다: 그대로 / 접기 / 숨기기(기록만 남김).
  - 숨기기: `cancelNotification`으로 알림창에서 지운다.
  - 접기: 원 알림을 지우고 Pushlog가 태그 단위 요약 알림을 하나 띄운다.
- 한 알림이 여러 태그에 걸리고 동작이 다르면 가장 보수적인 동작(그대로 > 접기 > 숨기기)을 따른다.
- 안전장치: 처음 숨기기를 설정할 때 "최근 7일 기준 이 규칙이면 N개가 숨겨진다" 미리보기. 정리한 개수를 요약 알림으로 알린다.
- 정리 모드를 끄면 태그별 동작은 무시되고 기록만 모드로 돌아간다.

### 6.6 안정성과 사용자 통제권

- 리스너 상태 감시: 끊김을 감지하면 `requestRebind`, 일정 시간 수신이 없으면 앱 안 배너와 알림으로 알린다. OEM별 배터리 최적화 예외 안내 화면을 둔다.
- 일괄 선택·삭제(앱/태그/방/기간 단위, 동작은 §6.9), 보관 기간 설정, 내보내기(형식은 빌더 판단, §9).
- 라이트/다크/시스템 테마 선택. 첫 화면 로딩은 원본 계층 전체를 읽지 않고 파생 테이블과 페이징으로 띄운다.
- 앱 단위 수집 제외 설정(특정 앱은 기록하지 않음). 새로 설치한 앱은 기본으로 수집 대상이다. 제외해도 그 앱의 기존 기록은 남고, 지우려면 사용자가 따로 삭제한다.

### 6.7 정보 추출

- **결제**: 카드 승인, 계좌 입출금, 구독 결제에서 금액, 가맹점, 수단, 승인/취소를 추출한다. 카드사 알림과 페이 알림이 같은 결제(금액 동일, 시각 근접)면 한 건으로 합친다. 월별·태그별 합계.
- **배송**: 쇼핑몰·택배사 알림에서 주문/출고/배송 완료 단계와 송장번호를 추출해 주문 단위 타임라인을 만든다. 외부 조회는 하지 않는다.
- **쿠폰/기프티콘**: 감지하면 등록을 제안하고, 만료일을 추출해 만료 전에 알린다. 바코드는 사용자가 사진을 고르면 ML Kit 바코드 스캐너로 읽는다. 사진은 저장하지 않고 읽은 바코드 값과 형식만 남기며, 화면에는 앱이 바코드를 다시 그린다. 등록한 쿠폰은 사용자 데이터(§5)다.
- **AI 질의**: Gemini Nano(ML Kit GenAI) 지원 기기에서만 노출한다. 금액·건수는 DB 집계로 계산하고, AI는 질문을 정해진 질문 유형 중 하나와 파라미터로 바꾸고 답 문장을 만드는 일만 한다. 답에는 근거 알림을 붙인다. 질문과 답은 기기 밖으로 보내지 않는다.
  - 처음 지원하는 질문 유형: 기간별 결제 합계, 태그·가맹점별 결제 합계, 안 읽은 메시지(대화방별), 특정 날짜·기간의 알림 목록. 유형 밖의 질문은 지원하지 않는다고 답한다. 유형은 나중에 늘린다.
- **추출 규칙 배포**: 규칙은 **앱에 내장**한다. 다만 Kotlin 코드가 아니라 데이터(발신 패키지·키워드 매칭 + 정규식 + 필드 매핑)로 표현해 assets에 둔다. 나중에 Remote Config로 옮길 때 형식을 바꾸지 않기 위해서다. 규칙 묶음에는 버전이 있고, 앱 업데이트로 버전이 오르면 §5 재계산으로 과거 기록에 다시 적용한다. 발신처 문구가 바뀌면 앱 업데이트로 고친다.

### 6.8 측정

- Crashlytics: 기본 활성.
- Analytics: 동의 시에만. 화면 진입, 설정 단계 완료 같은 사용 흐름.
- 안정성 지표(동의 여부와 무관하게 Crashlytics 비치명 이벤트 또는 동의 시 Analytics, 빌더 판단): 리스너 끊김·재연결 횟수, 패키지별 파싱 실패 수, 기기 제조사·OS 버전.
- §3의 금지 규칙을 따른다.
- `google-services.json`이 없으면 Firebase 없이 빌드되게 한다. CI와 로컬 개발은 이 파일 없이 돌아가야 한다. Firebase 프로젝트는 출시 준비 때 만든다.

### 6.9 삭제와 복구

- 사용자가 삭제한 기록(개별, 일괄)은 바로 지우지 않고 **삭제 표시**만 한다. 삭제 표시는 사용자 데이터(§5)이고, 표시된 기록은 목록·검색·통계·AI 질의·재계산 결과에서 빠진다.
- 삭제 후 **30일 동안** 휴지통 화면에서 되살릴 수 있다.
- 30일이 지나면 **원본까지 영구 삭제**한다. 원본 append-only 원칙의 유일한 예외다.
  - 메신저 메시지는 이후의 원본 행 여러 개의 누적 메시지 목록에도 들어 있다. 영구 삭제할 때는 그 메시지를 다른 원본 행에서도 지운다. 같은 메시지 식별 기준은 §6.2의 중복 제거 키다.
  - 영구 삭제는 주기 작업(WorkManager)이 한다.
- 보관 기간이 지난 기록도 같은 경로를 탄다. 보관 기간이 지나면 삭제 표시되고, 30일 뒤 영구 삭제된다.
- 휴지통 화면에서 즉시 영구 삭제도 할 수 있다.

## 7. 사용자가 정한 것

- 새 앱. 이름 Pushlog, 패키지 `com.citytexi.pushlog`.
- BM 제외(사전 준비 포함).
- `INTERNET` 권한 사용, Crashlytics 기본 + Analytics 동의 기반, 약속은 "알림 내용은 밖으로 나가지 않는다".
- 단톡방 묶기는 차별점이 아니라 기본 기능.
- 영구 기록 + 검색 + 복사 + 원래 앱 이동.
- 커스텀 분류는 태그 방식.
- 알림창 정리는 설정에서 고르는 선택 모드.
- 정보 추출(결제·배송·쿠폰·AI) 포함.
- 데이터 구조는 A(원본 + 파생).
- 삭제는 가리기 + 30일 내 복구, 30일 뒤 원본까지 영구 삭제.
- 추출 규칙은 앱 내장.
- 스타터 옵션: minSdk 26, nav3, CI는 `test`, `build-debug`, `ui-diff`.

## 8. 설계자 판단 (사용자 확인 필요 없음, 바꿔도 됨)

- 기본 보관 기간 무제한, 이미지 미저장.
- 규칙 변경 시 과거 소급, 수동 태그는 재계산이 덮어쓰지 않음.
- 정리 모드 기본값은 기록만, 다중 태그 충돌 시 보수적 동작 우선.
- 숨기기 미리보기와 정리 요약 알림.
- 원래 앱 이동은 `contentIntent` 캐시 → 런처 인텐트 대체.
- 원본은 압축 저장, 저장 공간 사용량 표시. 실측 후 재검토.
- 사용자 데이터(수동 태그, 쿠폰, 삭제 표시, 규칙·설정)는 파생 계층과 분리.
- 쿠폰 사진 미저장, 바코드 값만 저장.
- AI 질의는 정해진 질문 유형 4개로 시작.
- 추출 규칙은 데이터 형식(정규식 + 필드 매핑) + 버전.
- 수집 제외 앱의 기존 기록은 유지.
- 보관 기간 만료도 삭제 표시 → 30일 → 영구 삭제 경로.
- `google-services.json` 없이도 빌드.

## 11. 구현 첫 단계

발신처별 파서와 기본 태그 규칙은 실제 알림 원문이 있어야 만들 수 있다. 그래서 구현은 **수집기 먼저** 시작한다.

1. 리스너와 원본 저장만 있는 수집기를 만들어 개발자 기기에서 돌린다.
2. 카카오톡 `shortLabel` 실제 값, 메신저 원본 용량 증가량, 카드사·은행·페이·쇼핑몰·택배사 알림 원문 샘플을 모은다.
3. 모은 샘플을 테스트 픽스처로 써서 대화방 묶기, 기본 태그 규칙, 추출 규칙을 만든다. 픽스처에 들어가는 샘플은 개인정보를 가린 뒤 커밋한다.
